adabay

Rapid evaluation and calibration of Bayesian group sequential designs across common endpoint types.

v0.1.0 MIT R ≥ 4.0

Overview

adabay implements a semi-simulation framework for the rapid evaluation and calibration of two-arm Bayesian group sequential designs (GSDs). Trial data paths are generated by Monte Carlo simulation, while per-look posteriors and posterior tail probabilities are computed analytically or by low-dimensional deterministic quadrature. Conjugacy-preserving updates are obtained by approximating any user-specified prior by a finite mixture of conjugate components, and per-quantile tail-probability diagnostics flag insufficiently tight approximations.

The package offers a unified application programming interface for the four endpoint types most often encountered in confirmatory trials:

  • Continuous outcomes with normal–normal or normal–inverse-gamma conjugate updates.
  • Binary outcomes with beta–binomial conjugate updates.
  • Count outcomes with gamma–Poisson conjugate updates.
  • Time-to-event outcomes with gamma–exponential conjugate updates.

Across four worked case studies, one per endpoint type, adabay reproduces the operating characteristics of BATSS and adaptr within Monte Carlo error on the binary and continuous case studies (and of BATSS on the count case study), while running approximately four orders of magnitude faster than BATSS and approximately one to two orders of magnitude faster than adaptr per virtual trial at a common eight-core configuration and matched simulation budget.

Installation

Install the development version from GitHub:

# install.packages("devtools")
devtools::install_github("trilixlab/adabay")

Or install the release tarball directly from GitHub — no manual download needed:

install.packages(
  "https://github.com/trilixlab/adabay/releases/download/v0.1.0/adabay_0.1.0.tar.gz",
  repos = NULL, type = "source"
)

Or download the tarball from the Releases page and install it locally:

devtools::install_local("adabay_0.1.0.tar.gz")

The optional RBesT package is recommended for fitting non-conjugate priors via fit_mixture(). Plot methods use ggplot2 and ggsci when available, with a sensible base-graphics fallback.

Quick start

A typical workflow has four steps: build a design, a prior, and a decision rule, then call evaluate_design(). The same function is the entry point for both the single-design fused path (pass a adabay_design) and the cached grid-evaluation path (pass a adabay_cache produced by build_cache()).

library(adabay)

## 1. Design: 5-look binary GSD on the risk-difference scale (ADRENAL re-design)
des <- set_design(
  endpoint     = "binary",
  n_per_look   = c(760, 1520, 2280, 3040, 3800),
  effect_scale = "risk_difference",
  alternative  = "less"
)

## 2. Prior: independent Beta(1,1) on each arm
pri <- set_prior(
  endpoint = "binary",
  arms = list(c = list(family = "beta", a = 1, b = 1),
              t = list(family = "beta", a = 1, b = 1))
)

## 3. Decision: efficacy at P(Delta < 0) > 0.99, binding futility
dec <- set_decision(
  efficacy = list(list(threshold_effect = 0, threshold_prob = 0.99)),
  futility = list(list(threshold_effect = 0, threshold_prob = 0.90)),
  futility_binding = TRUE
)

## 4. Evaluate operating characteristics under H1 (fused path)
oc <- evaluate_design(des,
  prior    = pri, decision = dec,
  effect   = list(theta_c = 0.33, theta_t = 0.28),
  n_trials = 1e6,
  cores    = 8,
  seed     = 1L
)

print(oc); plot(oc); summary(oc)

Top-level functions

FunctionPurpose
set_design() Specify the design skeleton (endpoint, look schedule, scale).
set_prior() Specify per-arm conjugate or mixture-of-conjugate priors.
set_decision() Specify per-look efficacy and futility decision rules.
set_accrual() Specify recruitment, follow-up and dropout.
fit_mixture() Approximate a non-conjugate prior by a conjugate mixture.

Performance

The trial-simulation loop and the per-look posterior update are written in C++ via Rcpp using a 64-node Gauss–Legendre quadrature. The trial-level loop parallelises through parallel::mclapply (POSIX) or parallel::parLapply (Windows), with reproducibility within any fixed (seed, cores) pair guaranteed by the L'Ecuyer combined multiple-recursive generator.

Manuscript benchmarks (Tables 4–7) at the matched budget R = 10,000 and the R = 106 high-precision reference. adabay, adaptr and BATSS run on 8 cores; gsbDesign is analytic on a single core. Wall-clock is the sum of the paired H0 and H1 scenarios:

adabay runs on 8 CPU cores via mclapply with the L'Ecuyer combined multiple-recursive generator (cores = 8); adaptr on 8 cores via its native parallel backend; BATSS with 8 mclapply workers and INLA pinned to one thread per worker; gsbDesign analytic on a single core. Since the three simulation-based packages all run on 8 cores at the matched R = 10,000 budget, their wall-clock times are directly comparable at equal parallelism: the per-virtual-trial speedups of adabay on the binary case are approximately 31× versus adaptr (between one and two orders of magnitude) and approximately 1.6 × 104 × versus BATSS (four orders of magnitude). BATSS does not support time-to-event endpoints and adaptr covers only continuous and binary outcomes, so those comparisons are not constructible (reported as n/a in manuscript Tables 4–7).
